- [ ] Реалізувати редагування.

> Для password manager принципово важливо не зберігати паролі у відкритому вигляді. OWASP окремо описує практики secrets management і client-side encryption як підхід, за якого секрет лишається зашифрованим до моменту використання.

- [ ] Додати UX-повідомлення: "налаштуйте passkey / Touch ID / Face ID / Windows Hello".
- [ ] Протестувати на Chrome/Safari/Windows Hello/macOS.

### Epic 8. Toggle "зберігати на сервері"

**US-08.** Як користувач, я хочу мати перемикач збереження на сервері, щоб контролювати, чи буде мій personal item синхронізований.

Пропонована логіка:

- Для personal item: можна обрати server-synced або local-only.
- Для shared item: тільки server-synced, бо інакше sharing не працює.
- Якщо item local-only, користувач бачить попередження: "цей запис не буде доступний з іншого пристрою і не може бути відновлений адміністратором".
- Сервер ніколи не зберігає відкритий пароль. Якщо зберігає — то лише зашифрований об'єкт.

Задачі:

- [ ] Додати поле sync_mode.
- [ ] Додати UI toggle.
- [ ] Додати заборону local-only для shared records.
- [ ] Додати warning modal.
- [ ] Додати audit event для зміни sync mode.

**Оцінка:** 2–3 дні.

## User journeys

### Journey 1. Перший вхід користувача

Користувач відкриває веб-застосунок. Натискає "Sign in with Google". Його перекидає в Keycloak, а Keycloak — у Google Workspace. Користувач входить корпоративним Google-акаунтом. Після успішного входу Keycloak повертає його в застосунок. Якщо для користувача ще не налаштований passkey, система пропонує налаштувати біометрію / passkey як другий фактор.

**Результат:** користувач бачить свій vault.

### Journey 2. Створення нового пароля

Користувач натискає "Add password". Заповнює назву сервісу, URL, логін, пароль, notes. Обирає, чи це personal item, чи shared item. Для personal item бачить toggle: "зберігати на сервері". Якщо toggle увімкнено, запис зберігається в зашифрованому вигляді на сервері. Якщо вимкнено — запис local-only, без синхронізації.

**Результат:** пароль доступний у vault відповідно до обраного режиму.

### Journey 3. Шеринг пароля

Owner відкриває запис і натискає "Share". Обирає користувача або групу. Вказує роль: viewer або editor. Система перевіряє, що запис може бути shared. Якщо це local-only personal item, система просить спочатку увімкнути server sync. Після підтвердження інший користувач бачить цей запис у своєму vault.

**Результат:** пароль не пересилається вручну, доступ контролюється системою.

### Journey 4. Використання пароля

Користувач відкриває vault, знаходить потрібний запис через пошук або список. Натискає "Copy password". Пароль копіюється в clipboard на короткий час. Система фіксує audit event: користувач відкрив або скопіював запис.

**Результат:** користувач отримує доступ, але дія залишається контрольованою.

### Journey 5. Відкликання доступу

Owner відкриває shared item, заходить у "Manage access", видаляє користувача або групу. Після цього користувач більше не бачить запис у vault. Система створює audit event.

**Результат:** доступ централізовано відкликаний.

## Алгоритм роботи застосунку

Базовий алгоритм такий.

1. **Автентифікація.** Користувач заходить на сайт. Застосунок бачить, що він не авторизований, і перекидає його на Keycloak. Keycloak пропонує вхід через Google Workspace. Google підтверджує особу користувача. Keycloak створює сесію і видає застосунку токен. Backend на Java перевіряє цей токен і розуміє, хто саме зайшов.

2. **Робота з vault.** Після цього користувач відкриває vault. Коли він створює пароль, frontend шифрує або готує дані до безпечного збереження, backend приймає encrypted payload, записує його в базу, прив'язує до owner і прав доступу.

3. **Sharing і revoke.** Якщо користувач ділиться записом, backend додає permissions для іншого користувача або групи. Якщо доступ відкликається — permission видаляється або деактивується.

4. **Audit.** При кожній важливій дії система пише audit event: login, create, update, share, revoke, copy/view. Це потрібно не для "стеження", а для безпеки й розслідування інцидентів.
